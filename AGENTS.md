# AGENTS.md

Контракт для ИИ-агентов, работающих с этим репозиторием.

**Правка не считается завершённой, если после неё сломаны формат, линт, типы или тесты.**

## Перед началом работы

Прочитай `rpd.md` — это рабочий проектный документ с архитектурой, картой файловой структуры и справочником команд запуска. Общие правила пользователя (язык, стиль кода, стиль ответов) заданы в его личном файле `CLAUDE.md` и действуют поверх этого файла.

## Перед завершением работы

```bash
make check
```

Это разворачивается в следующую последовательность:

```bash
uv run --no-sync --frozen ruff format --check
uv run --no-sync --frozen ruff check
uv run --no-sync --frozen mypy
uv run --no-sync --frozen pytest
uv run --no-sync --frozen python -m scripts.validate_benchmark
```

Флаги `--no-sync --frozen` обязательны и стоят в `Makefile`: без них команда пересобирает окружение и может переписать `uv.lock`, тогда как CI ставит зависимости отдельным шагом `uv sync --locked`. На свежем клоне окружение разворачивается командой `make install`.

`make check` ничего не меняет в рабочем дереве — это ровно те проверки, что идут в CI. Автоисправления вынесены в отдельную цель `make fix` (`uv run ruff format` и `uv run ruff check --fix`); запускай её явно, когда действительно хочешь переписать файлы.

Отдельные цели: `make install`, `make lint`, `make fix`, `make typing`, `make test`, `make validate`. Цель по умолчанию — `check`.

`mypy` запускается без аргументов: список проверяемых директорий задан в `pyproject.toml` (`[tool.mypy] files`).

## Правила проекта

* Докстринги в проекте не требуются: правило `D` отключено в `[tool.ruff.lint] ignore`. Это снимает требование, а не запрещает докстринги и комментарии; запрет на комментарии — отдельное правило пользователя.
* Строгая зона типов — `src/`, `benchmark_generator/`, `sft/`: там действуют `disallow_untyped_defs` и `disallow_incomplete_defs`, то есть аннотации функций обязательны.
* Базовая зона — остальной свой код (`experiments/`, `scripts/`, `utils/`, `role/`, `tests/`, `evaluation_results/`, `evaluations/`): действует только `check_untyped_defs`. Каталог `log_analysis/` в проверки не входит: он целиком исключён из репозитория через `.gitignore` как локальные рабочие материалы.
* Вендоренный `metagpt/` не правится: он исключён из ruff (`extend-exclude`) и из mypy (`ignore_errors = true`).
* Данные задач `data/` не правятся и исключены из ruff вместе с `logs`, `log_archive` и `notebooks`.
* `pyproject.toml` — единственный источник конфигурации ruff, mypy и pytest. Версии инструментов тоже задаются только там: CI не пиннит ruff отдельным экшеном, а ставит группу `dev` из `uv.lock` (`uv sync --locked --only-group dev`) и запускает `uv run --no-sync ruff`, так что локальный `make lint` и CI всегда берут одну и ту же версию. Чтобы обновить ruff, поменяй спецификатор в группе `dev` и перегенерируй `uv.lock` — второго места правки нет.
* `uv.lock` — часть контракта: CI ставит зависимости с `--locked` и падает, если лок разошёлся с `pyproject.toml`. Меняешь зависимости — коммить обновлённый лок вместе с ними.

## CI

* На каждый push и pull request идут `lint`, `type-check`, `test`, `validate-benchmark`. Быстрая из них только `lint` (ставится одна группа `dev`); остальные три поднимают полное окружение проекта (несколько гигабайт вместе с `tensorflow`, `torch` и пакетами `nvidia`), поэтому у них стоит `timeout-minutes: 45`.
* Джоба `smoke` прогоняет `python -m experiments.evaluate --task_id <smoke_task_id> --model_id gt`, то есть оценивает эталонное решение из `data/{task_id}/gt/` его же метриками из `metric/{task_id}/metric.yaml`, и падает, если Completion Rate не равен 1.0. Джоба `changes` определяет по изменённым путям, какие именно задачи затронуты, и передаёт их список в `smoke` через `.github/scripts/select_smoke_tasks.sh`: скрипт отбрасывает задачи, чьи метрики требуют LLM- или VLM-судью, урезает список до `MAX_SMOKE_TASKS` и при пустом списке возвращает задачу по умолчанию `human_3`. Ручной запуск через `workflow_dispatch` с явным `smoke_task_id` работает по-прежнему. Задача по умолчанию выбрана без VLM-функций в `metric.yaml`, поэтому прогон не требует ни LLM, ни API-ключей. Для задач с VLM-функциями понадобится судья по изображениям (`VLM_JUDGE`, см. `src/vlm_utils.py`).
